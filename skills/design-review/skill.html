design-review

제품 맥락, 기존 design system, 접근성, 반응형 계층을 근거로 UI 경험을 리뷰하는 스킬입니다.

사용UI review, visual critique, layout, interaction, accessibility 판단
원문SKILL.md
기준references/design-review-criteria.md
검증node scripts/validate-skill.ts skills/design-review
중요한 기준 1

제품과 사용자를 먼저 봅니다.

target product의 도메인, 주 사용자, 반복 workflow, 업무 빈도를 바탕으로 severity를 정합니다.

중요한 기준 2

기존 design system을 우선합니다.

component convention, typography, spacing, state 규칙을 먼저 확인하고 개인 취향만으로 지적하지 않습니다.

중요한 기준 3

finding마다 evidence를 붙입니다.

screenshot, browser observation, code/CSS, design-system rule, WCAG, user/task evidence 중 최소 하나를 연결합니다.

중요한 기준 4

눈대중으로 pass를 선언하지 않습니다.

focus, target size, overflow, contrast, responsive 문제는 필요한 경우 browser-qa 관찰 증거로 확인합니다.

사용 판단

디자인 리뷰가 필요한지, 다른 스킬과 결합해야 하는지 먼저 분리합니다.

사용

화면 구조, visual hierarchy, interaction, state, accessibility, responsive layout, 제품 감각을 검토할 때 사용합니다.

결합

실제 브라우저 증거가 필요하면 browser-qa, 현재 best practice 확인이 필요하면 web-research와 결합합니다.

보류

대상 사용자, 주요 workflow, design system, viewport, evidence 범위가 불명확하면 먼저 scope를 좁힙니다.

차단

제품 맥락 없이 색감 취향만 말하거나, 모든 heuristic 위반을 동일한 bug로 단정하지 않습니다.

작업 흐름

리뷰는 발견 목록이 아니라 사용자 영향과 수정 방향까지 연결된 판단이어야 합니다.

1. 맥락 확인

제품 도메인, 사용자, 반복 workflow, device, design system을 확인합니다.

2. 화면 관찰

density, hierarchy, spacing, typography, state, responsive order를 봅니다.

3. 접근성 확인

focus, keyboard path, target size, contrast, error recovery를 점검합니다.

4. severity 판단

frequency, impact, persistence, domain/business risk로 등급을 정합니다.

5. 결과 작성

finding, evidence, user impact, recommendation, residual risk를 남깁니다.

Evidence Matrix

finding마다 적어도 하나의 근거를 붙이고, 추론은 추론이라고 표시합니다.

증거 유형

시각

screenshot, spacing, hierarchy, overlap, palette

상호작용

keyboard path, focus order, hover, loading, empty, error state

접근성

WCAG 2.2, contrast, focus visible, target size, error suggestion

코드

CSS, component rule, token, breakpoint, state handling

사용자 과업

task frequency, workflow speed, recovery path

조사 출처

요청 시 web-research로 source ledger와 채택 판단 기록

Severity 기준

등급은 heuristic 이름이 아니라 사용자 영향과 business risk로 정합니다.

S0
문제로 보지 않음 또는 의도된 trade-off
리뷰 대상에서 제외하거나 의도 근거만 기록합니다.
S1
polish/cosmetic
여유가 있을 때 수정해도 되는 표현, 정렬, 마감 문제입니다.
S2
friction
일부 사용자의 흐름을 늦추지만 주요 과업을 막지는 않습니다.
S3
major task risk
주요 workflow 성공률, 신뢰, 반복 업무 효율에 영향을 줍니다.
S4
release blocker
접근성, 안전, 법적/금전/데이터 손상, 되돌리기 어려운 action 위험입니다.

보안 경계

공유 취향은 보조 기준이며, 실제 severity는 맥락과 증거로 판단합니다.

허용

  • 조용한 운영 UI, 절제된 색, 얕은 border, stable dimension을 fallback taste로 사용합니다.
  • 제품군별 감각을 반영합니다. SaaS/CRM은 밀도, 콘텐츠 앱은 읽기 흐름, 게임은 즉각성을 우선합니다.
  • 위험한 action은 confirm, reverse, review path 유무를 높은 severity 판단에 포함합니다.

금지

  • 제품 맥락 없이 decorative orb, heavy gradient, nested card 같은 일반 금지만 반복하지 않습니다.
  • screenshot만 붙이고 finding, severity rationale, user impact를 생략하지 않습니다.
  • screen reader나 assistive tech를 실제로 검증하지 않았다면 검증했다고 말하지 않습니다.
