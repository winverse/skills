feature-workflow

이미 방향이 잡힌 프로젝트에서 하나의 기능, 이슈, 버그 수정, 세로 기능 단위를 검증 가능한 코드 변경으로 끝내는 반복 구현 스킬이다. 명세 확인, 작업 claim 대조, TDD 또는 특성화 증거, 구현, review, QA, 문서 동기화를 한 흐름으로 묶는다.

기존 명세 기반 구현 loop · TDD 증거 우선 · 병렬 작업 claim 확인 · 한국어 우선 · 정적 HTML

요약

이 스킬은 원시 아이디어를 다듬는 단계가 아니라, 이미 존재하는 PRD, 이슈, 명세, 버그 재현, 인수 기준, design.md, ADR을 실제 변경으로 완료하는 단계에서 사용한다.

  • 목적하나의 기능 작업을 계획, RED, GREEN, REFACTOR, review, QA, 문서 동기화까지 추적 가능한 증거와 함께 마무리한다.
  • 주요 입력현재 명세, 이슈, 인수 기준, 버그 재현, 프로젝트 지침, CONTEXT.md, ADR, PRD, design.md, work-claims.md.
  • 주요 출력출처가 표시된 primitive 목록, 구현 계획, RED/GREEN/REFACTOR 증거, runtime 또는 browser QA, review 결과, 문서 동기화 메모, 완료 보고.
  • 반복 위치project-workflow가 만든 기준 문서 이후에 여러 번 호출되는 기능 개발 루프다.
  • 멈춤 조건원시 제품 아이디어, 구조 선택, 초기 디자인 시스템, claim 충돌, 보안 gate 미정, CommonJS 도입 요구가 나오면 구현 전에 정리한다.

사용 판단

요청이 “무엇을 만들지”보다 “정해진 요구사항을 어떻게 구현해 끝낼지”에 가깝다면 이 스킬을 선택한다.

사용한다기존 PRD, 이슈, 명세, 버그 재현, 인수 기준, design.md, ADR이 있고 구현, 수정, 검증, 완료 보고가 필요할 때.
되돌린다도메인, 제품 가치, architecture boundary, 프로젝트 구조, design baseline이 아직 정해지지 않았으면 project-workflow로 넘긴다.
큰 구현계획 review와 병렬 session이 필요하면 writing-plans, plan-eng-review, subagent-driven-development를 출처가 표시된 primitive로 선택한다.
UI 작업design.md와 선택된 mock 방향을 확인하고, design review와 browser QA 증거를 완료 조건에 포함한다.
CLI 또는 API 작업browser가 없으면 명령 출력, fixture, API 응답, log 같은 non-browser runtime 증거를 남긴다.

중요한 기준

  • 출처 표시Superpowers plugin, GStack plugin, Matt Pocock skills, repo-local helper에서 고른 primitive는 <source package>: <exact name> -> selected | skipped | fallback 형태로 기록한다.
  • 권위 문서CONTEXT.md, CONTEXT-MAP.md, ADR, PRD, design.md, domain-first folder map, folder-local instruction docs가 있으면 명세 해석의 authority로 사용한다.
  • 작업 claimwork-claims.md가 있으면 production edit 전에 현재 lane의 claimed write set, read-only paths, shared/hotspot files, integration owner를 확인한다.
  • TDD 계약코드 제품 repo에서는 production change 전에 failing test, characterization check, repro script 중 하나로 RED evidence를 남긴다. 불가능하면 예외와 대체 evidence를 기록한다.
  • TypeScript module 정책type: "module", import/export, ESM tsconfig를 유지하고 CommonJS, require, module.exports, .cjs, .cts를 새로 도입하지 않는 CommonJS 금지 기준을 지킨다.

작업 흐름

  1. 1명세와 지침 확인현재 명세, 이슈, PRD, ADR, design.md, local instructions, workflow-state, work-claims를 읽는다.
  2. 2primitive inventory필요한 upstream 또는 repo-local primitive만 고르고 출처와 상태를 기록한다.
  3. 3범위와 claim 대조인수 기준, 제외 범위, 의도한 write set, active claim overlap, TypeScript module 정책을 확인한다.
  4. 4계획 review구현 접근과 2-5분 단위 계획, 검증 명령을 만들고 plan review 또는 fallback review를 거친다.
  5. 5RED 작성TDD 또는 특성화 테스트로 실패 증거를 먼저 남긴다. domain invariant는 가능한 한 domain package나 pure function test에서 시작한다.
  6. 6구현과 GREEN최소 변경으로 GREEN을 만들고, 필요한 경우 behavior를 바꾸지 않는 REFACTOR와 검증 명령을 남긴다.
  7. 7review와 QAcode review, design review, browser QA 또는 non-browser runtime 증거를 수행하고 보류 항목은 명시한다.
  8. 8문서 동기화와 완료docs drift, folder-local instruction update 필요성, artifact hygiene, eval seed 후보, commit handoff 여부를 정리한다.

조건부 허용

항목기준
subagent fan-out큰 기능이나 이슈에서만 사용한다. 작업은 겹치지 않는 write set으로 나누고, 다음 작업이 결과에 막히면 main agent가 직접 처리한다.
write-capable tooltool, MCP, external API, file write, network, untrusted content가 있으면 Agent Tool And Security Risk Gate를 확인하거나 작성한 뒤 진행한다.
commit handoff사용자가 commit을 요청했을 때만 atomic-committer로 넘긴다. 넘긴 뒤에는 해당 스킬의 push 계약을 따른다.

차단

항목기준
claim 충돌다른 active lane의 claimed write set과 겹치면 overlap block으로 멈추고 integration owner 또는 사용자에게 조정을 요청한다.
read-only pathread-only paths는 조사와 참고만 허용한다. patch를 만들지 않는다.
CommonJS 금지TypeScript production edit에서 CommonJS, require, module.exports, .cjs, .cts를 새로 추가하지 않는다. 명세가 요구하면 차단 사유, migration boundary, 사용자 확인을 남긴다.
shared skills repo hook이 repo 자체에는 제품 코드용 TDD hook을 설치하거나 실행하지 않는다. 대상 코드 repo에 적용할 문서 계약과 eval fixture만 유지한다.
