- For updating, revising, maintaining, renaming, splitting, deprecating, or otherwise changing an existing shared skill, use the shared skill at `<skills-root>/skills/skill-update/SKILL.md`.
- For commit requests, split dirty files into logical changesets and use the shared skill at `<skills-root>/skills/atomic-committer/SKILL.md`.

- For choosing, creating, standardizing, or refactoring frontend, backend, full-stack monorepo, desktop app, infrastructure-aware folder structures, or folder-local `AGENTS.md` indexes, use the shared skill at `<skills-root>/skills/project-structure/SKILL.md`.

- For existing PRD/issue/spec/bug implementation with TDD, implementation planning, review, QA/runtime evidence, document sync, and completion reporting, use the shared skill at `<skills-root>/skills/feature-workflow/SKILL.md`.
- Treat `project-workflow` + `feature-workflow` as the Workflow suite: setup writes the authority plus `workflow-state.md` cache and, when parallel sessions are possible, `work-claims.md`; implementation reads and updates those coordination artifacts while producing evidence.
- In target code repos, `feature-workflow` may be paired with a project-local TDD hook that requires RED evidence, characterization evidence, or an explicit TDD exception before production code edits. Do not install that hook globally or inside the shared skills repo.
- For documentation refresh, stale-doc review, conflicting repo instructions, or stale folder-local `AGENTS.md` indexes, use the shared skill at `<skills-root>/skills/sync-docs/SKILL.md`.
- For polishing transcript text, lecture scripts, subtitles, meeting notes, or long prose by direct reading without scripted replacement, use the shared skill at `<skills-root>/skills/transcript-polisher/SKILL.md`.
- For using spare token or context budget productively, improving agent skill usage, making skills easier to invoke, adding or reviewing validators, aligning documentation, creating self-improvement loops, or raising repo quality through tests, hooks, docs, evals, and review automation, use the shared skill at `<skills-root>/skills/agent-improvement-loop/SKILL.md`.
- For setting up, scaffolding, configuring, or improving an evaluation harness for agent skills, agent instructions, prompt routing, cross-agent portability, tool choice, guardrails, artifact hygiene, or repeatable AI-agent workflows, use the shared skill at `<skills-root>/skills/agent-eval-harness/SKILL.md`.
- For browser runtime verification, Playwright checks, screenshots, console or network inspection, accessibility snapshots, broken links, responsive layout checks, text overlap detection, or `skill.html` rendering QA, use the shared skill at `<skills-root>/skills/browser-qa/SKILL.md`.
- For code review, PR review, diff review, implementation audit, regression risk review, missing test review, maintainability review, or JavaScript and TypeScript style review, use the shared skill at `<skills-root>/skills/code-review/SKILL.md`.

## Project Skill Overrides

- Prefer this project's local docs, source code, and logs before general web results.
- Use repo-linked custom skills before default/global agent behavior when the behavior overlaps.
- When using `show-skills`, prefer the live listing script and `docs/skill-catalog.md`; do not install or globally register skills while listing them.
- When using `web-research` for verified, broad, or high-stakes topics, use the smallest safe research budget, then query fan-out, source ledgers, evidence scoring, counterexample search, and stop rules.
- Treat `web-search`, `web search`, `웹서치`, and `웹 검색` as aliases for `web-research`.
- Treat any user request that invokes `web-research` or its aliases as an explicit request for parallel sub-agent fan-out, delegation, and parallel agent work for the research portion. Use single-agent research only when the user explicitly asks for it, private data is involved, runtime/tool policy blocks delegation, or the task is a tiny official quick check; state the skip reason when using this exception.
- Treat web research that feeds a recommendation, comparison, implementation plan, skill update, PR, architecture note, or product decision as verified search unless one official source fully settles it.
- When using `karpathy-thinkings`, think before coding, avoid silent assumptions, prefer simple implementations, make surgical changes, and verify success criteria.
- When using `skill-update`, read `docs/update-source-registry.md` first, treat every invocation as an original/upstream provenance preflight, use `.gitmodules` as the canonical source for vendored plugin/submodule update candidates, keep `SKILL.md`, references, validators, `agents/openai.yaml`, `skill.html`, snippets, docs, and history aligned; if a source is found or suspected, verify that source with `web-research` first, then record adopt/adapt/reject/defer decisions in `docs/update-source-registry.md` before applying local deltas; do not update plugin packages, MCP config, or submodules incidentally through `skill-update`; when the user explicitly includes plugin updates, use the plugin update lane and keep `.gitmodules`, `docs/plugin-catalog.md`, `Plugin update list`, validators, and history aligned; run `scripts/validate-source-registry.ts` when registry or workflow usage maps change.
- When using `atomic-committer`, scan candidate commits for forbidden secret-bearing content, hard-block live-looking credential assignments and private-key material across common providers, update `.gitignore` for repeatable untracked local or secret-bearing artifacts that should never be committed, group dirty files by logical changeset, write commit messages with an English conventional prefix and Korean summary, and push after committing unless the user explicitly asks not to push. If remote, branch, or upstream is missing, commit locally and report why push could not run.
- When using `pull-request`, check branch/base/head/remote state, `gh auth status`, and existing PR state before creating or updating a PR; run `gh pr create` only when the user explicitly asks to create a PR, and do not merge, close, reopen, delete branches, enable auto-merge, or force-push without an explicit request.
- When leaving PRs for this skills repo, write Korean PR title/body and use `.github/pull_request_template.md`; skill-change PRs must mention the Korean-first `skills/**/*.md` rule and include `node scripts/validate-korean-markdown.ts .` in validation.
- When using `project-structure`, default to Bun, Turborepo, Next.js, NestJS with Fastify, GraphQL, urql, GraphQL Code Generator, PostgreSQL + Drizzle, Panda CSS with headless UI, Tauri, Zod env validation, and Pulumi/Docker/AWS ECR/ECS Fargate when infrastructure is requested unless the project says otherwise.
- When using `project-structure`, use MongoDB + Atlas when MongoDB/document DB is selected, and Supabase Postgres when managed psql-compatible Postgres is selected. Keep Supabase service-role keys and MongoDB URIs server-only.
- When using `project-structure`, keep app env/codegen paths consistent and place monorepo Redis boundaries in `packages/db/src/redis`, with API cache wrappers under `apps/api/src/providers/cache`.
- When using `project-structure`, include the selected project's test, security, health/readiness, observability, Panda CSS, GraphQL generated artifact, and Drizzle migration boundaries in the final tree.
- When using `project-structure`, document agent tool, MCP, external API, DB shell, migration, deploy script, destructive command, secret, and scrubbed artifact boundaries when they are part of the structure.
- When using `project-structure`, include `infra/pulumi`, app-local Dockerfiles, AWS ECR image ownership, and one selected AWS runtime path, ECS Fargate or EC2 Docker host, only when infrastructure or deployment structure is requested.
- When using `project-structure` with infrastructure, include the public entrypoint choice, required secret names, Pulumi stack config examples without live values, immutable image tag handoff, and a post-deploy smoke check.
- When using `project-structure`, add short folder-local `AGENTS.md` indexes for meaningful boundary folders and keep them as table-of-contents files rather than copied root rules.
- When a request is raw product discovery, domain modeling, new-project planning, PRD/issues, project structure setup, or design baseline setup, use `project-workflow` before `project-structure` or `feature-workflow`.
- When using `project-workflow`, choose only needed setup primitives from Matt Pocock skills, GStack plugin, Superpowers plugin, design-direction, and repo-local custom helpers; mark each as `selected`, `invoked`, `skipped`, `fallback`, or `deferred`. Invoke selected originals when the runtime exposes them, use fallback interview questions only when the original surface is unavailable, and use `deferred` for primitives that must wait for domain/product/design/tool gate answers. Label borrowed names with their source package, for example Matt Pocock skills `grill-with-docs`, GStack plugin `office-hours`, Superpowers plugin `brainstorming`, repo-local custom `project-structure`, and user custom `design.md`. For raw ideas, the first response must run or fallback in this order: `grill-with-docs`, `office-hours`, Superpowers `brainstorming` setup gap check; `design.md`, `project-structure`, PRD, and issue backlog stay `deferred` or `not created yet` until those answers exist. `grill-me` is not the default project setup gate.
- When using `project-workflow`, write initial setup artifacts and project docs in Korean first unless the user or target project explicitly sets another language; preserve exact code identifiers, commands, file paths, product names, API names, and upstream skill/plugin names. Treat this as a Korean-first artifact gate: before reporting completion, check `CONTEXT.md`, ADR, PRD, issue backlog, `design.md`, setup validation, `workflow-state.md`, `work-claims.md`, and phase handoff; if their natural-language titles/body/lists, `work-claims.md` lane/field labels, or phase step headings/descriptions are English-centered, rewrite them Korean-first and report the evidence. In the first response for a raw idea, ask the domain/product fallback questions first and mark artifact paths as target/proposed/not created yet until files are actually written.
- When a workflow uses TypeScript, keep ESM only across setup and implementation: `package.json` `type: "module"`, ESM `tsconfig`, `import`/`export`, and no CommonJS, `require`, `module.exports`, `.cjs`, or `.cts`.
- When `project-workflow` prepares parallel work, create `.scratch/<slug>/work-claims.md` with lane id, owner/session, branch or worktree, claimed write set, read-only paths, shared/hotspot files, integration owner, status, validation command, and evidence path.
- When `project-workflow` prepares a large implementation handoff, create a phase/step handoff under `.scratch/<slug>/phases/index.json` or equivalent with self-contained steps for Codex, including read files, claimed write set, acceptance commands, blocked conditions, and summary field. Optional runner scripts must be TypeScript and Codex-first, not Python or permission-bypass based.
- When `project-workflow` needs folder/env/codegen/db/infra structure, call `project-structure` only after domain language and concrete architecture questions exist; use it as an architecture handoff before ADR/PRD, not as raw idea discovery.
- When a spec, issue, bug report, acceptance criteria, ADR, PRD, or `design.md` already exists and the user wants implementation, use `feature-workflow`.
- When using `feature-workflow`, choose only needed implementation primitives from Superpowers plugin, GStack plugin, Matt Pocock skills, and repo-local helpers. Label borrowed names with their source package, for example Superpowers plugin `writing-plans`/`tdd`/`subagent-driven-development`, GStack plugin `plan-eng-review`, Matt Pocock skills `diagnose`, and repo-local `code-review`/`browser-qa`/`sync-docs`.
- When using `skill-update` for a repo-wide external dependency refresh, treat it as a dependency update sweep: check all `.gitmodules` vendored plugins, repo-owned plugins, `docs/update-source-registry.md` workflow primitive lane, and workflow `upstream-dependency-map.md` usage maps before reporting completion.
- When `work-claims.md` exists, `feature-workflow` must confirm the current lane owns the intended write set before production edits, stop with an overlap block when another active lane owns the same file or module, and leave shared/hotspot files to the named integration owner.
- When `feature-workflow` lacks implementation helper skills, mark fallback and create issue-level implementation design, exact TDD or characterization plan, RED/GREEN/REFACTOR evidence, and non-browser runtime evidence when no browser surface exists.
- When either workflow touches tools, MCP, external APIs, write-capable automation, network access, or untrusted content, record the Agent Tool And Security Risk Gate before implementation.
- In this repo, `/goal` means Claude Code's `/goal` feature. For long `project-workflow` or `feature-workflow` runs on Claude Code, propose a goal condition with measurable end state, check evidence, constraints, and turn/time bound; on other runtimes, write the same content as a completion checklist.
- When workflow routing needs repeatable behavior checks, call `agent-eval-harness` as a separate validation layer and seed cases for `project-workflow` routing, `feature-workflow` routing, dependency inventory, `project-structure` timing, PRD settings, UI mockup selection, `work-claims.md` lane ownership, overlap block, CLI/no-browser evidence, MCP/API gate decisions, fallback lane, project setup verification, completion mapping, document sync, artifact hygiene, and goal condition quality.
- When using `sync-docs`, treat current repo files as the first evidence source, refresh folder-local `AGENTS.md` indexes when folder trees change, verify target project skill setup when instruction links/snippets change, and ask before changing a documentation rule when the source of truth is unclear.
- When using `transcript-polisher`, keep editing judgment manual: scripts may discover files, line numbers, and section counts only; split by paragraph or lecture section, delegate one section per subagent when runtime permits, preserve lecture examples and generated awkward-output examples, and include Claude `/goal`-style completion evidence for long reviews.
- When using `agent-improvement-loop`, choose the skills-repo track for skill catalogs and the general-repo track for application or library repos; before any spend-down run, ask `남은 토큰을 최대한 사용해서 안전한 backlog를 처리할까요? (예/아니오)`; if the answer is yes, run safe backlog items in small multi-agent batches; if no, treat token budget as a ceiling and review one lane at a time; prefer durable artifacts such as docs, validators, tests, hooks, snippets, or eval cases over chat-only advice; use Claude Code `/goal` only when bounded by measurable end state, check evidence, constraints, and turn/time/item limit.
- When using `agent-eval-harness`, start with a small repo-local deterministic harness under `evals/agent/`, define success criteria before cases, record `agentSurfaces` and `assumptionDate` for fast-changing agent behavior, prefer deterministic checks such as `required_link_count`, `required_file_reference`, and `json_schema`, include the minimum safety case pack and artifact scrub policy, keep live model/API evals advisory until budget and flake policy are explicit, turn real agent failures into minimal regression cases, and test `/goal`-style condition quality with deterministic text checks when relevant.
- When using `browser-qa`, report URL, viewport, evidence, reproduction step, severity, and cleanup; close Playwright/Chrome tabs and stop any local HTTP/dev server started for QA unless the user explicitly needs it kept running; keep subjective design critique in `design-review`.
- When using `code-review`, lead with findings and file/line references; for JS/TS prefer clear functional collection style where it improves clarity, without forcing it over simpler loops; include agent/tool-call boundaries, prompt injection, destructive side effects, least privilege, approval, and secret/private-data scrubbing when the diff touches those surfaces.
- When using `design-review`, respect the target project's existing design system and product domain first; use quiet operational UI, restrained color, shallow borders, stable dimensions, 8px-or-less radius, no decorative orbs/gradients/bokeh, and no nested cards only as the shared fallback profile.
